# Efficient iteration and publication

Use the existing project checklist, campaign and installer. This guide adds no
second ledger, automatic acceptance, retry policy or cloud authorization.

## Choose the next test from the observed failure

| Changed boundary | First discriminating check | Required follow-up |
| --- | --- | --- |
| Prompt or decision schema | Recorded input at that node, including the failing output | Real model positive and negative control; affected path |
| Retrieval query or normalization | Same connector input and recorded provider output | One authorized live connector check when its remote contract changed |
| Parallel workers | Overlapping controlled tasks, failure drainage and isolated state | Integrated path with source-tagged events |
| Final synthesis or transformation | Saved accepted report and original evidence | Attribution, omitted material caveats and valid abstention controls |
| Packaging or deployment | Package/layout/runtime inspection | Same candidate served in native TEST, then authorized publication |

Use `test --cases <file> --case <id> --plan` before a paid experiment, then the
same selected case for execution. Use `experiment diagnose --receipt <file>`
and `experiment compare --baseline <file> --candidate <file>` on saved local
runs before repeating retrieval. These commands do not replace semantic review.
Run the repository's full validation at its required final boundary; do not
repeat it after an unchanged check or replace it with focused tests.

New node evidence can survive an unrelated plan edit when its recorded criterion
binding is identical. The binding includes the criterion, node context, requirement
reference, publication policy and that criterion's scope-decision history. Package,
configuration, evaluator, execution environment and case/mode remain strict.
The report exposes `evidence_reused`, the original plan hash and `reuse_basis`;
it never rewrites the receipt. Historical receipts without the new binding retain
whole-plan matching. Exclusion/reactivation does not resurrect older acceptance.
The final `__agent__` acceptance always retains whole-plan matching.

This does NOT reuse evidence across changed code, prompts, models or environments.
The plugin has no proven per-test transitive source dependency map. Such changes
still require revalidation. Use affected-path prioritization to reduce exploratory
work, then complete required integrated checks. Use `progress report` to rebuild
derived reporting without rerunning completed calls. Graph/checkpoint replay is
distinct from reading a saved result: replay can execute nodes and effects, so
inspect the application's actual branch.

## Resume the existing publication operation

1. Read the owner's operation journal and its current candidate. If an installer
   owns locks/recovery, invoke its existing adapter; do not bypass it with a
   competing coordinator or invent a universal installer receipt schema.
2. Reconcile a pending native operation using `native status`. A pending status
   is neither failure nor success; do not submit a second deployment to poll it.
3. For a new authorized publication, inspect `native publish`, then use its
   `--apply` route under that same owner. Preserve prior deployment recovery.
4. Verify served source/runtime and the required functional cases independently.
5. Use `registry inspect` and `registry readiness`. For an existing same-agent
   registration whose deployment binding changed, inspect the new card and use
   `registry adopt --registry-key <existing-key>`; do not create another record.
6. A portal URL and Registry readiness do not prove a working chat. Perform the
   requested client acceptance and record its outcome separately.

These are existing composable operations, not a new one-command deployment API.
Remote errors after possible submission remain uncertain until scoped readback
proves their outcome. Reuse established authorization; ask again only for a
genuinely new scope or an explicit approval-system requirement.

## Report evidence, not optimistic stages

Use `workflow status` for a consolidated local observation. Add `--native` to
read and reconcile existing deployment state and inspect Registry readiness.
Neither mode starts research, publishes or registers. Local derived reports and
existing reconciliation receipts may be updated. Exit success means required
observations completed, NOT that deployment or quality was accepted; read each
section. Errors remain errors rather than being converted into missing resources.
The actual client conversation is always a separate verification.

Record candidate identity, observed stage, receipt, observation time, next action
and unresolved effects in the existing project checklist. Distinguish:

- locally tested;
- TEST active and served candidate verified;
- native functional case accepted;
- PROD active and served candidate verified;
- Registry ready;
- actual client conversation accepted;
- quality calibrated on a named finite set.

Never derive the later states from an earlier one. A historical replay proves
compatibility with that saved result, not new research. An abstention may prove
a safety control while failing the useful-answer criterion. Report elapsed time,
model calls, actor runs and confirmed cost separately; unknown cost is not zero.
Claim speed improvement only with comparable cases, evidence, model and clocks.

## Turn real incidents into calibration controls

Use `quality calibrate` / `quality assess` and their existing hashed source
bindings. Keep labels outside model input. Add reviewed contrastive examples
to the project's corpus; do not ship private captured posts or receipt data in
the plugin. An anonymized or synthetic example must be identified as such.

| Failure class | Positive control | Negative control |
| --- | --- | --- |
| Cross-source attribution | Attribute each location/claim to its actual source | Attach source A's location to source B |
| Missing evidence | State that a source returned no usable evidence | Assert nobody discussed the subject on that platform |
| Sample scope | Describe the captured sample with its limits | Infer population sentiment or sales from a few posts |
| Transformation | Preserve supported facts and material caveats | Drop an essential caveat or invent an action |
| Valid abstention | Decline only the unsupported claim, preserve original report | Claim verification or references that are absent |

Require positive and negative controls for the rubric and inspect disagreements.
A schema-valid judge output is not evidence of a correct judgment. Offline fixture
passes validate evaluator mechanics, not real judge calibration. Keep technical
failures, semantic failures, abstentions and stale evidence separate; no universal
80% threshold or self-awarded acceptance. Locate the first altered/omitted fact
across retrieval, analysis, repair and synthesis before changing the prompt.

## Official basis and limits

- [LangGraph testing](https://docs.langchain.com/oss/python/langgraph/test)
  documents individual-node tests and partial execution. It does not authorize
  automatic reuse of this plugin's acceptance receipts.
- [LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence)
  distinguishes checkpoint state and stores; application effects still need their
  actual recovery contract. It is not an Oracle installer journal specification.
- [LangSmith evaluation approaches](https://docs.langchain.com/langsmith/evaluation-approaches)
  separates single-step, trajectory and final-response evaluation and explains
  why end-to-end response evaluation alone is slower and harder to diagnose.

The operational sequence above is this plugin's verified CLI contract, not an
Oracle-mandated workflow. Native API references remain in native-cli.md and
registry.md. No remote API, provider capability or quality threshold is added here.
